Write the initial implementation of **`bctow`**, a **topic-based pub/sub** library for **high-throughput networked streaming servers** in **Rust (stable)**.

### Primary goals

- **Ergonomic, elegant API**
- **Millions of msgs/sec** design point
- Optimize steady-state for **~16KB payloads**
- **Bounded memory**, **no allocations in steady-state hot paths** (publish + poll/recv)
- **Thread-safe**
- **No async runtime dependency**
- **Single producer** (exactly one publisher thread), **many consumers**

### Core architecture (non-negotiable)

- There is a **single shared log/ring buffer per topic**.
- Each `ConsumerClient` has a **cursor per subscribed topic**.
- **Clients are responsible for keeping up**: if a client lags beyond retention capacity, it will miss messages according to an explicit overflow policy.

### Public API shape

Expose:

- `Producer<T>` (single-producer only)
  - Fast path: `publish_id(topic: TopicId, msg: T)`
  - Convenience: `publish(topic: impl TopicKey, msg: T)` that interns/resolves topic (allowed to allocate only if a new topic is created)

- `ConsumerContext<T>`
  - Create/destroy `ConsumerClient<T>` dynamically
  - Allow clients to subscribe/unsubscribe dynamically

- `ConsumerClient<T>`
  - Poll/receive APIs that do not allocate in steady-state
  - Ability to update subscriptions at runtime

Provide compile-able usage examples.

### Topics and matching

- Start with **exact topic matching** only.
- Architect topic representation to allow future **prefix/wildcard matching**:
  - Use types to encode match kind (e.g., `ExactTopic`, `TopicPattern`, `MatchKind`) while only implementing `Exact` now.

- Use a **topic interner**:
  - Convert topic strings to a stable, compact `TopicId`.
  - Publishing hot path should operate on `TopicId` (no string work).

### Message representation

Pick the representation that best balances performance and ergonomics for **~16KB payloads**:

- Avoid allocations in steady-state hot paths.
- Support a **configurable max payload size**.
- Define behavior when payload > max (return an error; do not panic).

### Concurrency + fairness

- **Single producer** appends to per-topic logs without locking in the hot path (SPSC/MPSC not required for publish, but consumers are concurrent).
- Many consumers read via per-client cursors.
- Prefer client fairness over raw throughput when forced to choose:
  - Avoid systematic starvation of slower or less-active clients.

### Backpressure / overflow policies

If simple enough, support explicit overflow policies such as:

- `DropOldest`
- `DropNewest`
- `SkipToLatest` (consumer jumps forward on overrun)

If multiple policies aren’t clean initially, implement one policy but keep the enum/type boundary.

### Metrics

Metrics are nice to have, but must **not impact performance** in the hot path:

- Use relaxed atomics and/or feature-gated collection.
- Keep counters off critical inner loops.

### Type-system invariants

Use types to prevent invalid states:

- `TopicId` is a distinct type.
- Separate exact-topic vs pattern-topic types even if patterns aren’t implemented yet.
- Clients cannot outlive their context (lifetimes or `Arc` ownership).
- Correct `T` bounds (`Send + Sync + 'static` as required).

### Deliverables

1. Minimal working implementation (`lib.rs` or small module set) providing:
   - `Producer<T>`, `ConsumerContext<T>`, `ConsumerClient<T>`
   - topic interner + `TopicId`
   - per-topic ring/log + per-client cursors
   - configurable max payload + overflow policy

2. Short design explanation (data structures, memory layout, concurrency model, fairness strategy).
3. Tests:
   - single producer / single consumer
   - single producer / many consumers
   - dynamic subscribe/unsubscribe while publishing
   - lagging consumer overrun behavior (policy verified)

4. No async runtime dependency
