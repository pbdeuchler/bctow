# Benchmark Suite for bctow

## Context

bctow makes specific performance claims: no broker lock on hot-path `publish_id`, no allocations in steady-state publish or receive. This benchmark suite validates those claims, characterizes scaling behavior, and surfaces architectural limits — particularly the `readers` atomic contention cliff and `poll()`'s O(subscriptions) scan cost.

## Architecture Decisions

**Dual harness**: Criterion for single-threaded micro-benchmarks (per-operation latency with statistical rigor). Custom harness with pre-spawned threads and `Barrier` synchronization for multi-threaded scaling benchmarks — Criterion's warm-up/iteration model produces misleading results at high thread counts where OS scheduler variance dominates.

**Consumer multiplexing**: macOS caps thread creation at ~2-4K per process. For consumer counts exceeding available threads, distribute N consumers across a thread pool of min(N, thread_ceiling) threads. Each thread owns a batch of `ConsumerClient` instances and polls them round-robin. For contention-specific benchmarks, use thread-per-consumer up to OS limits to maximize concurrent `readers` atomic pressure.

**Message types**: `u64` (8B baseline), `FixedBytes<64>`, `FixedBytes<512>`, `FixedBytes<4096>`. Ring capacity must be reduced for large T x many topics: at capacity 32, 10K topics of `FixedBytes<4096>` is ~1.3GB. All benchmarks should document their memory footprint assumptions.

**Metrics**: Latency per operation is the primary measurement (ns/op). Throughput (msg/sec) is derived for presentation. All `poll()` results wrapped in `std::hint::black_box()` to prevent dead code elimination.

## Step 1: Infrastructure and Harness

Add Criterion to `[dev-dependencies]` in `Cargo.toml`. Add `[[bench]]` target pointing to `benches/benchmarks.rs`. Create the bench file with a shared harness module (inline `mod harness`) containing:

- **`setup_broker<T>(topics, capacity)`** — creates broker, registers N topics by name pattern, returns `(Producer<T>, ConsumerContext<T>, Vec<TopicId>)`
- **`spawn_consumers<T>(ctx, topic_ids, count, threads)`** — creates ConsumerClient instances, subscribes each to all provided topics, distributes across threads, blocks all on a shared `Barrier`. Returns a handle that can release the barrier and wait for drain completion.
- **`drain_loop<T>(clients, barrier, messages_expected, counter)`** — per-thread loop: wait on barrier, poll all owned clients in round-robin until `AtomicUsize` counter reaches expected total, signal done.
- **Fixture helpers**: `fill_fixed_bytes<N>() -> FixedBytes<N>` producing deterministic non-zero fill patterns.

The harness determines the thread ceiling empirically at startup (attempt thread spawns until failure, cache the result). Benchmarks parameterize consumer count; the harness silently multiplexes when count exceeds ceiling.

**Files**: `Cargo.toml`, `benches/benchmarks.rs`

**Verify**: `cargo bench --all-features --no-run` compiles without error.

## Step 2: Single-Threaded Operation Benchmarks (Criterion)

Criterion group `operations` measuring per-call latency with no threading overhead. Each benchmark uses 1 topic, 1 consumer, default ring capacity 1024.

- **`publish_id_warm`**: Pre-register topic, publish one message via `publish_id` to warm the cache, then bench subsequent `publish_id` calls. This is the idealized hot path — no lock, no lookup.
- **`publish_string_lookup`**: Same setup, but call `publish("topic_name", &val)` instead. Delta vs `publish_id_warm` isolates the `RwLock` read + HashMap lookup cost.
- **`poll_hit`**: Publish a message, then bench `poll()` when a message is available. Measures `read_into` + copy cost.
- **`poll_miss`**: Consumer subscribed, no messages pending. Bench `poll()` returning `None`. Measures the scan overhead baseline.

Criterion group `message_size` — separate benchmark functions per T (compile-time monomorphization). For each of `u64`, `FixedBytes<64>`, `FixedBytes<512>`, `FixedBytes<4096>`: publish + poll round-trip. 1 topic, 1 consumer. This isolates `copy_nonoverlapping` cost scaling with `size_of::<T>()`.

**Files**: `benches/benchmarks.rs`

**Verify**: `cargo bench --all-features -- operations` and `cargo bench --all-features -- message_size` produce Criterion output with stable variance.

## Step 3: Multi-Threaded Scaling Benchmarks (Custom Harness)

Custom harness group `scaling`. Each benchmark pre-spawns threads, uses barrier synchronization, measures only the publish-to-drain window. Reports throughput (msg/sec) and per-message latency to stdout.

- **`consumer_scaling`**: 1 topic, `u64` messages, 1000 messages published. Consumer counts: [1, 10, 50, 100, 250, 500, 1000, 2000]. Fine granularity in 50-500 range to locate the `readers` atomic contention cliff (expected around 50-100 on typical hardware — producer's spin in `push()` waiting for `readers == 0` becomes the bottleneck). Thread-per-consumer up to OS ceiling; multiplexed above.
- **`topic_scaling`**: 1 consumer subscribed to all topics, `u64`, 100 messages per topic. Topic counts: [1, 10, 100, 1000, 10000]. At 10K topics this primarily measures `poll()`'s O(N) HashMap scan over subscriptions, not ring performance. Document this clearly in output.
- **`combined_scaling`**: [10 topics x 100 consumers, 100 topics x 10 consumers, 100 topics x 100 consumers]. 100 messages per topic. Shows interaction between both dimensions.

**Files**: `benches/benchmarks.rs`

**Verify**: `cargo bench --all-features -- scaling` completes without thread-spawn failures and produces monotonically increasing latency across consumer/topic counts.

## Step 4: Pathological and Stress Benchmarks

Custom harness group `stress`. Designed to surface worst-case behaviors and architectural limits.

- **`contention_cliff`**: 1 topic, `FixedBytes<512>`, 500 messages, consumer counts [1, 2, 4, 8, 16, 32, 64, 128, 256, 512]. Thread-per-consumer (no multiplexing). Very fine-grained power-of-2 sweep to precisely locate where per-publish latency jumps from nanoseconds to microseconds. This documents the `readers` spin-wait cliff — the most important architectural limit.
- **`sparse_poll`**: 10K topics registered, 1 consumer subscribed to all 10K, but messages published to only 1 topic. Bench poll-to-receive latency. Surfaces the O(10K) scan cost per successful `poll()`. Pathological case for the round-robin subscription iteration.
- **`overflow_policy_comparison`**: 1 topic, ring capacity 32, 100 consumers, producer publishing at 2x aggregate consumer drain rate (consumers insert artificial delay between polls). Run with each of `DropOldest`, `DropNewest`, `SkipToLatest`. Report messages received vs published per consumer to quantify drop behavior alongside latency.
- **`large_message_fanout`**: 1 topic, `FixedBytes<4096>`, 100 messages, consumer counts [10, 50, 100, 500]. At 500 consumers x 4KB, each publish drives ~2MB of DRAM reads. Surfaces memory bandwidth ceiling (expect ~1000 msg/sec at 500 consumers on typical DDR4).

**Files**: `benches/benchmarks.rs`

**Verify**: `cargo bench --all-features -- stress` completes. `contention_cliff` output shows a visible latency inflection point. `sparse_poll` latency is >> single-topic `poll_hit` baseline. `overflow_policy_comparison` shows measurably different message counts per policy.

## Acceptance Criteria

1. `cargo bench --all-features` compiles and runs all benchmark groups to completion without panic or OOM
2. Criterion benchmarks (`operations`, `message_size`) produce stable results with < 5% variance across runs
3. Custom harness benchmarks print structured output: benchmark name, parameters, messages/sec, ns/op
4. Consumer scaling benchmarks demonstrate a visible contention inflection point in the output
5. `sparse_poll` latency scales linearly with subscription count relative to `poll_hit` baseline
6. Overflow policy comparison shows distinguishable behavior across all three policies
7. No modifications to library source code — benchmarks use only the public API
8. All benchmarks use `--all-features` flag per project convention
